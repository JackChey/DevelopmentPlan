## 1. 文档说明

### 1.1 文档目的

本文用于定义系统中需要幂等保护的接口边界、幂等 Key 使用规范、响应缓存边界、失败结果处理策略、状态码约定、风险项以及生产环境落地要求。

目标是保证在客户端重试、网络超时、服务重启、MQ 重复投递、第三方重复回调、多实例并发等场景下，业务不会被重复执行，尤其避免重复下单、重复支付、重复退款、重复扣减库存、重复发放权益等问题。

### 1.2 适用范围

适用于以下类型的接口或任务：

- 会创建、修改、删除业务数据的接口。
- 涉及资金、库存、优惠券、积分、权益、订单状态变更的接口。
- 外部第三方回调接口。
- MQ 消息消费逻辑。
- 定时补偿任务、批处理任务、数据同步任务。
- 需要支持客户端或网关自动重试的接口。

### 1.3 不适用范围

以下场景通常不需要接入业务幂等机制：

- 普通只读查询。
- 分页查询。
- 字典数据读取。
- 静态配置读取。
- 不产生业务副作用的统计查询。

如果查询行为会产生副作用，例如写入浏览记录、增加阅读数、触发异步任务，则应将副作用部分单独纳入幂等或防重策略。

### 1.4 术语定义

| 术语            | 说明                                                                    |
| --------------- | ----------------------------------------------------------------------- |
| 幂等            | 同一个业务请求执行一次或多次，最终业务结果一致。                        |
| Idempotency-Key | 客户端或服务端生成的幂等请求唯一标识。                                  |
| 请求体 Hash     | 对业务请求内容计算得到的摘要，用于判断同一个 Key 是否被用于不同请求体。 |
| 首次响应        | 同一个幂等请求第一次执行完成后保存的响应结果。                          |
| 重复请求        | 使用相同幂等 Key 和相同请求体再次发起的请求。                           |
| 处理中状态      | 首次请求已登记但业务逻辑尚未最终完成。                                  |
| 确定性失败      | 同样请求再次提交仍然会失败的业务失败，例如订单已关闭。                  |
| 不确定性失败    | 无法确认业务最终结果的失败，例如第三方接口超时。                        |

## 2. 幂等设计原则

### 2.1 哪些场景必须幂等

只要接口具备以下特征之一，就应纳入幂等设计：

- 会改变业务状态。
- 会产生资金、库存、权益、积分、优惠券等资源变更。
- 会调用第三方系统并产生外部副作用。
- 会被客户端、网关、MQ、定时任务重试。
- 存在用户重复点击、网络抖动、服务超时、异步补偿等重复执行风险。

### 2.2 哪些场景不需要幂等

只读查询通常不需要业务幂等。查询接口的关注点是缓存、权限、数据隔离和性能，不应把普通查询强行接入幂等 Key。

### 2.3 幂等 Key 的作用边界

幂等 Key 不应全局裸用，必须绑定业务作用域。推荐作用域如下：

```text
租户ID + 用户ID/商户ID + 接口标识 + Idempotency-Key
```

如果系统没有租户，可以去掉租户维度；如果是开放平台接口，应使用商户 ID、应用 ID 或合作方 ID 作为隔离维度。

### 2.4 幂等与防重提交的区别

防重提交主要防止短时间内重复点击，通常依赖按钮禁用、验证码、短 TTL 锁或前端控制。

幂等是服务端业务正确性保障，需要在服务端保存处理状态、请求 Hash、业务结果或响应结果。前端防重不能替代服务端幂等。

### 2.5 幂等与缓存的区别

幂等响应缓存只服务于“同一个业务请求重复提交时返回首次结果”，不是通用接口缓存。

普通缓存关注命中率和性能；幂等缓存关注业务一致性和重复请求处理。401、403、权限结果、当前请求上下文、敏感数据等不应作为幂等响应缓存。

### 2.6 幂等与分布式锁的关系

分布式锁只能减少并发进入业务逻辑的概率，不能独立保证幂等。锁可能超时、误释放、Redis 故障，也无法表达业务最终状态。

生产环境应使用以下组合：

```text
幂等记录 + 请求 Hash + 业务唯一索引 + 业务状态机 + 必要时分布式锁
```

### 2.7 Redis、数据库、业务状态机的职责划分

| 组件          | 职责                           | 说明                           |
| ------------- | ------------------------------ | ------------------------------ |
| Redis         | 加速、短期锁、短期状态缓存     | 不应作为资金类幂等的唯一保障。 |
| 数据库        | 唯一约束、最终记录、事务一致性 | 关键业务必须有数据库兜底。     |
| 业务状态机    | 判断业务是否允许再次执行       | 防止状态回退和重复流转。       |
| MQ 消费记录表 | 记录消息消费结果               | 防止重复消费造成重复副作用。   |

| 批量导入  | 通常是       | 防止重复导入同一批数据。         |

| 数据同步  | 是           | 防止重复应用同一变更。           |
| 对账任务  | 是           | 对账任务通常会重复扫描。         |

## 4. 不需要幂等的接口清单

### 4.1 普通查询接口

普通 GET 查询不改变业务状态，不需要 Idempotency-Key。

### 4.2 分页查询接口

分页查询关注查询条件、排序稳定性、性能和权限隔离，不需要幂等机制。

### 4.3 字典查询接口

字典查询可以做普通缓存，但不属于业务幂等。

### 4.4 详情查询接口

详情查询本身不需要幂等。如果详情查询会记录浏览足迹或增加计数，应将写入部分单独设计为可重复执行。

### 4.5 配置读取接口

配置读取属于只读场景，不需要幂等。

### 4.6 报表查询接口

报表查询通常不需要幂等。若报表接口会创建导出任务，则导出任务创建需要幂等。

### 4.7 只读统计接口

只读统计不需要幂等，但应关注缓存一致性和权限隔离。

### 4.8 特殊说明：查询接口存在副作用时的处理

如果查询接口包含以下副作用，应拆分副作用逻辑并单独进行幂等或去重：

- 阅读数增加。
- 浏览记录写入。
- 最近访问时间更新。
- 查询触发异步任务。
- 查询触发外部通知。

## 5. 幂等 Key 规范

### 5.1 哪些接口必须传 Idempotency-Key

所有被标记为必须幂等的同步写接口，均应要求客户端传入 `Idempotency-Key`。

对于 MQ 消费、第三方回调、定时任务等非客户端直传场景，应使用业务流水号、消息 ID、第三方流水号或任务批次号作为幂等标识。

### 5.2 Key 的生成方

| 生成方                     | 适用场景                                   |
| -------------------------- | ------------------------------------------ |
| 客户端生成                 | 用户发起的创建、支付、退款、提交类请求。   |
| 服务端生成                 | 服务端先创建业务草稿，再由客户端确认提交。 |
| 第三方流水号复用           | 支付回调、退款回调、物流回调。             |
| MQ MessageId 或业务事件 ID | 消息消费场景。                             |

### 5.3 Key 的格式要求

建议要求：

- 长度 16 到 128 个字符。
- 只允许字母、数字、短横线、下划线、冒号。
- 不允许空字符串。
- 不允许包含敏感业务信息，例如手机号、身份证、银行卡号。

### 5.4 Key 的长度限制

建议最大长度为 128。开放平台或多业务复合 Key 可放宽到 256，但必须有明确索引设计，避免数据库索引过长。

### 5.5 Key 的唯一性范围

推荐唯一范围：

```text
tenant_id + user_id/merchant_id + api_code + idempotency_key
```

不建议只对 `idempotency_key` 做全局唯一，避免不同用户或不同租户之间互相冲突。

### 5.6 Key 的有效期

有效期应大于客户端最大重试窗口和业务补偿窗口。

| 业务类型       | 建议有效期         |
| -------------- | ------------------ |
| 普通提交类接口 | 10 分钟到 24 小时  |
| 创建订单       | 24 小时到 7 天     |
| 支付/退款      | 7 天到 90 天       |
| MQ 消费记录    | 7 天到 180 天      |
| 账务流水       | 长期保存或永久保存 |

### 5.7 Key 的复用规则

同一作用域内：

- 同 Key + 同请求体：视为重复请求，返回首次结果或当前处理状态。
- 同 Key + 不同请求体：视为冲突，返回 409。
- Key 过期后再次使用：可视为新请求，但高风险业务应通过业务唯一索引继续兜底。

### 5.8 Key 缺失时的处理

对必须幂等的接口，缺少 `Idempotency-Key` 应返回：

```text
400 Bad Request
```

普通查询接口不应要求传入该 Header。

### 5.9 Key 非法时的处理

Key 长度、字符集、格式不符合要求时，应返回：

```text
400 Bad Request
```

### 5.10 Key 被恶意刷爆时的防护

应结合以下手段：

- 限制 Key 长度。
- 用户、租户、IP、商户维度限流。
- 对未认证请求不创建幂等记录。
- 控制 Redis 和数据库 TTL。
- 异常高频 Key 创建触发告警。

## 6. 请求体一致性校验

### 6.1 请求体 Hash 的必要性

请求体 Hash 用于判断同一个幂等 Key 是否被错误复用于不同业务请求。

如果不校验请求体 Hash，客户端可能用同一个 Key 提交两个不同订单，服务端却返回第一次请求的响应，造成严重业务错误。

### 6.2 Hash 计算范围

应纳入 Hash 的内容：

- 业务参数。
- 请求路径或接口标识。
- HTTP Method。
- 影响业务结果的 Header。
- 当前用户、租户或商户标识。

### 6.3 不应纳入 Hash 的字段

以下字段通常不应纳入 Hash：

- TraceId。
- Timestamp。
- Nonce。
- Signature。
- 客户端版本号。
- 设备信息。
- 纯日志字段。

如果某个字段会影响业务决策，则应纳入 Hash。

### 6.4 同 Key 同请求体的处理

同 Key 同请求体表示重复请求：

- 首次请求成功：返回首次响应。
- 首次请求处理中：返回 409 或 202。
- 首次请求确定性失败：按失败缓存策略返回首次失败。
- 首次请求结果未知：返回处理中或引导客户端查询业务状态。

### 6.5 同 Key 不同请求体的处理

同 Key 不同请求体必须返回：

```text
409 Conflict
```

响应中应明确错误码，例如：

```text
IDEMPOTENCY_KEY_CONFLICT
```

### 6.6 请求体 Hash 冲突风险

推荐使用 SHA-256。Hash 仅用于一致性校验，不应作为安全签名。安全签名应使用独立的 HMAC 或非对称签名机制。

### 6.7 文件上传、批量导入场景的 Hash 策略

文件上传和批量导入应结合以下内容计算 Hash：

- 文件内容 Hash。
- 文件大小。
- 文件名或业务批次号。
- 导入类型。
- 用户或租户标识。

大文件不建议将完整文件内容写入幂等记录，可只保存文件 Hash、批次号和业务摘要。

## 7. 幂等状态模型

### 7.1 INIT：初始化

请求已进入幂等流程，但尚未正式执行业务逻辑。该状态可选，简单实现可以直接从 `PROCESSING` 开始。

### 7.2 PROCESSING：处理中

幂等记录已创建，业务逻辑正在执行。

重复请求命中该状态时，应返回 409 或 202，而不是再次执行业务逻辑。

### 7.3 SUCCESS：处理成功

业务逻辑已成功完成，幂等记录已保存首次响应或业务结果。

重复请求应返回首次成功响应：

```text
200 OK + 首次响应
```

### 7.4 FAILED：处理失败

业务处理失败。是否缓存失败结果取决于失败类型：

- 确定性失败：可以缓存并返回首次失败。
- 不确定性失败：不应简单缓存失败，应进入 `UNKNOWN` 或允许重试。

### 7.5 UNKNOWN：结果未知

业务执行结果无法确认，例如第三方接口超时、事务提交结果未知、服务进程崩溃。

该状态应通过补偿任务、主动查询或业务表反查确认最终结果。

### 7.6 EXPIRED：记录过期

幂等记录已超过有效期，可被清理。高风险业务即使幂等记录过期，也应依赖业务唯一索引、业务流水号或状态机继续兜底。

### 7.7 状态流转规则

推荐状态流转：

```text
INIT -> PROCESSING -> SUCCESS
INIT -> PROCESSING -> FAILED
INIT -> PROCESSING -> UNKNOWN -> SUCCESS
INIT -> PROCESSING -> UNKNOWN -> FAILED
SUCCESS -> EXPIRED
FAILED -> EXPIRED
```

禁止状态回退，例如：

```text
SUCCESS -> PROCESSING
SUCCESS -> FAILED
FAILED -> PROCESSING
```

除非有明确的人工修复或补偿流程。

### 7.8 状态机异常处理

如果状态停留在 `PROCESSING` 超过合理时间，应由补偿任务扫描并处理：

- 能从业务表确认成功：更新为 `SUCCESS`。
- 能确认失败且未产生副作用：更新为 `FAILED` 或允许重试。
- 无法确认：更新为 `UNKNOWN` 并告警。

## 8. 响应缓存边界

### 8.1 可以缓存的响应

可以缓存以下响应：

- 首次成功响应。
- 明确的业务失败响应。
- 同 Key 不同请求体冲突响应。
- 资源状态不允许导致的确定性失败。

### 8.2 不能缓存的响应

以下结果不应作为幂等响应缓存：

- 401 未认证。
- 403 无权限。
- 当前请求上下文。
- 权限判断结果。
- 敏感数据。
- 临时 Token。
- Set-Cookie 相关响应。
- 用户个性化且 Key 维度不足的响应。
- 系统 500 异常。
- Redis、数据库、MQ 等基础设施异常。

### 8.3 响应体缓存内容

建议只缓存必要响应：

- HTTP 状态码。
- 业务错误码。
- 业务消息。
- 业务 ID。
- 必要的展示数据。

不建议缓存完整上下文、敏感字段、权限结果和一次性令牌。

### 8.4 响应体过大时的处理

如果响应体过大，不建议完整缓存。可改为缓存业务 ID，然后重复请求时根据业务 ID 重新查询当前可见结果。

### 8.5 只缓存业务 ID 的策略

对于订单、支付、退款等业务，推荐保存：

```text
business_type + business_id + status + response_code
```

重复请求时根据业务 ID 查询业务表并构造响应。

### 8.6 重复请求返回首次响应的规则

重复成功请求应返回：

```text
200 OK + 首次响应
```

如果首次创建接口返回 201，重复请求是否继续返回 201 或改为 200，需要团队统一。推荐重复请求返回 200，并保持响应体与首次成功结果一致。

## 9. 失败结果缓存策略

### 9.1 失败分类

| 类型           | 说明                       | 是否建议缓存       |
| -------------- | -------------------------- | ------------------ |
| 确定性失败     | 同样请求再次提交仍然失败。 | 可以               |
| 不确定性失败   | 无法确认业务是否成功。     | 不建议             |
| 系统性失败     | 基础设施、程序异常。       | 不建议             |
| 第三方未知失败 | 第三方超时、网络中断。     | 不建议直接缓存失败 |

### 9.2 可以缓存的失败

以下失败可以缓存：

- 业务参数校验失败。
- 业务规则失败。
- 资源状态不允许。
- 余额不足。
- 库存不足。
- 订单已关闭。
- 同 Key 不同请求体。
- 唯一约束冲突且能映射到已有业务结果。

### 9.3 不建议缓存的失败

以下失败不建议缓存：

- 数据库连接失败。
- Redis 超时。
- MQ 发送失败。
- 第三方接口超时。
- 网络超时。
- 事务提交结果未知。
- 系统 500 异常。
- 线程中断、进程重启、容器被杀导致的中间状态。

### 9.4 参数格式错误是否占用幂等 Key

建议策略：

```text
请求体格式错误、字段类型错误、缺少必填字段：不创建幂等记录。
```

原因是此类错误通常发生在业务处理前，用户修正参数后应允许继续使用同一个 Key。

### 9.5 业务校验失败是否占用幂等 Key

建议策略：

```text
业务规则校验失败：可以创建幂等记录并缓存失败结果。
```

例如订单已关闭、库存不足、余额不足，这些属于明确业务结果。

### 9.6 失败后是否允许重试

| 失败类型       | 是否允许同 Key 重试 | 说明                       |
| -------------- | ------------------- | -------------------------- |
| 参数格式错误   | 允许                | 未创建幂等记录。           |
| 业务确定性失败 | 通常不允许          | 返回首次失败即可。         |
| 系统异常       | 允许                | 不缓存失败。               |
| 第三方超时     | 不直接重试业务提交  | 应进入查询确认或 UNKNOWN。 |
| MQ 发送失败    | 视事务边界决定      | 需要 Outbox 或补偿机制。   |

### 9.7 UNKNOWN 状态的补偿策略

`UNKNOWN` 状态必须有补偿策略：

- 通过业务表反查。
- 通过第三方查询接口确认。
- 通过 MQ Outbox 重新投递。
- 超过阈值后人工介入。
- 记录告警并阻止重复执行高风险动作。

## 10. 状态码约定

### 10.1 缺少 Idempotency-Key

必须幂等的接口缺少 Key：

```text
400 Bad Request
```

### 10.2 Key 格式非法

```text
400 Bad Request
```

### 10.3 正在处理

同步接口推荐：

```text
409 Conflict
```

异步接口推荐：

```text
202 Accepted
```

团队必须二选一或按同步/异步明确区分，不能同一接口随机返回。

### 10.4 同 Key 不同请求体

```text
409 Conflict
```

### 10.5 重复成功请求

```text
200 OK + 首次响应
```

### 10.6 首次创建成功

创建类接口可返回：

```text
201 Created
```

也可统一返回：

```text
200 OK
```

### 10.7 业务校验失败

可选：

```text
400 Bad Request
```

或：

```text
422 Unprocessable Entity
```

建议团队统一，不要混用。

### 10.8 未认证

```text
401 Unauthorized
```

不缓存幂等响应。

### 10.9 无权限

```text
403 Forbidden
```

不缓存幂等响应。

### 10.10 系统异常

```text
500 Internal Server Error
```

不缓存为确定失败。

## 11. 存储设计

### 11.1 Redis 存储方案

Redis 适用于：

- 短期幂等记录。
- 分布式锁。
- 高频低风险接口。
- 响应摘要缓存。

不建议 Redis 作为资金、账务、库存等核心业务的唯一幂等依据。

### 11.2 数据库存储方案

数据库适用于：

- 核心业务幂等记录。
- 资金、订单、退款、库存、权益等强一致场景。
- 需要审计和长期追踪的业务。

### 11.3 Redis + 数据库组合方案

推荐组合：

```text
Redis：快速判断、减少并发、短期状态。
数据库：唯一约束、最终记录、审计追踪。
业务表：业务状态机和业务唯一键兜底。
```

### 11.4 幂等记录表设计

建议字段：

| 字段                  | 说明                   |
| --------------------- | ---------------------- |
| id                    | 主键。                 |
| tenant_id             | 租户 ID。              |
| user_id / merchant_id | 用户或商户标识。       |
| api_code              | 接口或业务操作标识。   |
| idempotency_key       | 幂等 Key。             |
| request_hash          | 请求体 Hash。          |
| business_type         | 业务类型。             |
| business_id           | 业务 ID。              |
| status                | 幂等状态。             |
| response_code         | 首次响应状态码。       |
| response_body         | 首次响应体或响应摘要。 |
| error_code            | 错误码。               |
| error_message         | 错误信息摘要。         |
| created_at            | 创建时间。             |
| updated_at            | 更新时间。             |
| expired_at            | 过期时间。             |

### 11.5 唯一索引设计

推荐唯一索引：

```text
tenant_id + user_id/merchant_id + api_code + idempotency_key
```

业务表也应有业务唯一索引，例如：

```text
order_no
payment_no
refund_no
transaction_no
message_id + consumer_group
```

### 11.6 请求 Hash 字段

`request_hash` 应有普通索引或与幂等 Key 一起存储，用于快速判断同 Key 是否被复用到不同请求。

### 11.7 业务 ID 字段

`business_id` 用于重复请求时反查业务结果，也用于处理“业务成功但幂等响应保存失败”的场景。

### 11.8 响应结果字段

响应字段可以保存完整响应，也可以保存响应摘要。高风险接口建议至少保存业务 ID、状态码、错误码和必要结果。

### 11.9 过期时间字段

`expired_at` 用于清理历史幂等记录。清理时应分批执行，避免大事务和锁表。

### 11.10 状态字段

状态字段必须支持：

```text
PROCESSING
SUCCESS
FAILED
UNKNOWN
EXPIRED
```

简单场景可省略 `INIT`。

### 11.11 幂等记录清理策略

清理策略应满足：

- 按业务类型设置不同 TTL。
- 分批清理。
- 保留核心资金流水长期审计记录。
- 清理任务本身必须幂等。
- 清理失败可重试。

## 12. 分布式锁策略

### 12.1 是否必须使用分布式锁

不一定。若数据库唯一索引和幂等记录插入能够原子保障，并发控制可以主要依赖数据库。

分布式锁适合减少并发压力，但不应替代数据库唯一索引。

### 12.2 Redis 锁使用场景

适用场景：

- 短时间内高并发重复点击。
- 避免大量请求同时进入数据库。
- 降低第三方接口重复调用概率。

### 12.3 锁 Key 设计

推荐：

```text
lock:idempotency:{tenantId}:{userId}:{apiCode}:{idempotencyKey}
```

### 12.4 锁超时时间

锁 TTL 应大于接口常规处理耗时，并小于异常场景可接受阻塞时间。

资金、退款、库存等高风险接口，应结合业务处理时间、第三方超时、补偿机制综合确定。

### 12.5 锁续期机制

长耗时任务需要锁续期，或者不依赖锁覆盖整个业务执行过程，而是依赖幂等记录状态和业务唯一约束。

### 12.6 锁释放安全性

释放锁时必须校验锁持有者标识，避免释放其他实例持有的锁。

### 12.7 锁过期导致并发进入的处理

锁过期后并发进入时，应由以下机制兜底：

- 幂等记录唯一索引。
- 业务表唯一索引。
- 业务状态机。
- 第三方业务流水号。

### 12.8 数据库唯一索引兜底

生产环境不应只相信锁。关键业务必须通过数据库唯一索引保证最终不会重复创建业务记录。

## 13. 事务边界设计

### 13.1 幂等记录与业务数据是否在同一事务

能放在同一数据库事务内的，应尽量放在同一事务内，确保业务数据和幂等状态一致。

如果跨数据库、跨服务或涉及第三方调用，则需要状态机、Outbox、补偿任务处理最终一致。

### 13.2 业务成功但幂等记录保存失败

必须支持从业务表反查最终结果。幂等记录不能成为唯一结果来源。

处理方式：

- 业务表保存业务流水号或幂等 Key。
- 捕获幂等记录保存失败并告警。
- 重复请求时通过业务唯一索引查询已有业务结果。

### 13.3 幂等记录成功但业务执行失败

如果业务未产生副作用，可更新为 `FAILED` 或删除记录允许重试。

如果失败结果不确定，应更新为 `UNKNOWN` 并进入补偿流程。

### 13.4 事务提交结果未知

例如数据库提交超时、连接中断。不能直接认为失败，应通过业务主键、唯一键或流水号反查。

### 13.5 本地事务与外部调用的边界

外部调用不能放入数据库本地事务中保证原子性。应通过业务流水号、第三方幂等号、查询确认、补偿任务和状态机保证最终一致。

### 13.6 Outbox 模式

业务成功后需要发送 MQ 的场景，推荐使用 Outbox：

```text
本地事务内同时写业务表和消息表。
后台任务扫描消息表并投递 MQ。
投递成功后标记已发送。
消费者侧仍然做幂等消费。
```

### 13.7 Saga / 补偿事务

跨服务长事务可采用 Saga。每一步操作都应具备：

- 正向幂等。
- 反向补偿幂等。
- 状态机约束。
- 可查询的业务流水号。

## 14. 典型流程设计

### 14.1 创建订单幂等流程

```text
1. 校验 Idempotency-Key。
2. 计算请求体 Hash。
3. 尝试创建 PROCESSING 幂等记录。
4. 如果记录已存在：
   - Hash 不同：返回 409。
   - SUCCESS：返回首次响应。
   - PROCESSING：返回 409 或 202。
   - FAILED：按失败策略处理。
5. 校验商品、价格、库存、优惠券。
6. 创建订单，订单号唯一索引兜底。
7. 更新幂等记录为 SUCCESS。
8. 返回订单创建结果。
```

### 14.2 支付提交幂等流程

```text
1. 校验 Idempotency-Key 和支付流水号。
2. 创建支付单或查询已有支付单。
3. 使用支付流水号调用第三方支付。
4. 第三方超时不得直接标记失败。
5. 进入支付中状态并等待回调或主动查询。
6. 支付成功后按支付流水号入账，唯一索引兜底。
7. 重复请求返回已有支付状态。
```

### 14.3 退款申请幂等流程

```text
1. 校验 Idempotency-Key。
2. 校验订单是否可退款。
3. 创建退款单，退款单号唯一索引兜底。
4. 调用支付渠道退款，传入退款流水号。
5. 渠道超时进入 UNKNOWN 或 REFUNDING。
6. 通过回调或主动查询确认退款结果。
7. 重复请求返回已有退款单状态。
```

### 14.4 消息消费幂等流程

```text
1. 获取 message_id、business_id、consumer_group。
2. 尝试插入消费记录 PROCESSING。
3. 如果已 SUCCESS，直接 ack。
4. 如果 PROCESSING 超时，根据策略重试或跳过并告警。
5. 执行业务逻辑，业务唯一索引兜底。
6. 更新消费记录为 SUCCESS。
7. ack 消息。
```

### 14.5 第三方回调幂等流程

```text
1. 验证签名。
2. 获取第三方流水号。
3. 查询本地业务单据。
4. 判断状态是否允许流转。
5. 已处理成功的回调直接返回成功。
6. 状态不一致或回退请求拒绝处理并记录日志。
7. 更新业务状态和回调记录。
```

### 14.6 定时补偿任务幂等流程

```text
1. 扫描待补偿业务记录。
2. 按业务 ID 获取执行锁或创建任务执行记录。
3. 判断当前业务状态。
4. 仅对允许补偿的状态执行。
5. 补偿成功后更新状态。
6. 重复扫描时根据状态跳过。
```

### 14.7 批量导入幂等流程

```text
1. 计算文件 Hash 和批次号。
2. 创建导入批次记录。
3. 若批次已存在，返回已有批次状态。
4. 每行数据使用业务唯一键或行级 Hash 去重。
5. 记录成功、失败、跳过数量。
6. 支持重复查询导入结果。
```

## 15. 多实例部署要求

### 15.1 本地内存锁不可用

多实例部署下，本地内存锁只能保护单个进程，不能保护整个服务集群，不应用作幂等保障。

### 15.2 多实例并发请求处理

多实例并发时必须依赖共享存储：

- 数据库唯一索引。
- Redis 原子操作。
- MQ 消费记录表。
- 分布式状态机。

### 15.3 Redis 集群场景

Redis 集群下应关注：

- Key 分片。
- 锁实现正确性。
- 主从切换造成的锁丢失。
- Redis 短暂不可用时的降级策略。

### 15.4 数据库主从延迟问题

幂等判断和业务唯一性校验应读主库或使用强一致读。不能在写入后立刻读从库判断是否存在。

### 15.5 服务重启后的幂等恢复

服务重启后，应通过数据库或 Redis 中的幂等记录恢复状态。长时间 `PROCESSING` 记录应由补偿任务处理。

### 15.6 灰度发布期间的兼容性

灰度期间不同版本服务可能同时处理请求。幂等 Key 生成、Hash 算法、状态码、数据库字段必须保持兼容。

## 16. 消息消费幂等

### 16.1 消息唯一 ID

消息必须具备唯一标识，优先使用业务事件 ID，而不是仅依赖 MQ 自动生成的 MessageId。

### 16.2 消费记录表

建议唯一索引：

```text
message_id + consumer_group
```

不同消费者组可独立消费同一消息。

### 16.3 消费状态

建议状态：

```text
PROCESSING
SUCCESS
FAILED
UNKNOWN
```

### 16.4 重复消息处理

重复消息命中 `SUCCESS` 时应直接 ack，不重复执行业务逻辑。

### 16.5 消息乱序处理

需要状态机防止旧消息覆盖新状态。例如订单已完成后，不允许延迟到达的已支付消息把状态回退。

### 16.6 消费失败重试

消费失败后是否重试取决于失败类型：

- 系统异常：允许重试。
- 业务确定性失败：记录失败并告警或进入死信。
- 不确定结果：进入 UNKNOWN，等待补偿确认。

### 16.7 死信消息处理

死信恢复处理也必须走同一套消费幂等逻辑。

### 16.8 业务唯一约束兜底

消费幂等记录不能替代业务唯一约束。入账、发券、加积分等业务表仍需唯一流水号。

## 17. 第三方接口与回调幂等

### 17.1 第三方请求流水号

调用第三方接口时，应传入本地唯一业务流水号。该流水号应可用于第三方侧幂等和后续查询。

### 17.2 本地业务流水号

本地必须保存：

- 本地业务单号。
- 第三方流水号。
- 请求状态。
- 回调状态。
- 最后查询时间。

### 17.3 第三方超时处理

第三方超时不能直接标记业务失败，应进入：

```text
PROCESSING
```

或：

```text
UNKNOWN
```

然后通过主动查询或回调确认结果。

### 17.4 主动查询确认

对于支付、退款、签约等核心场景，必须提供主动查询确认机制，不能只依赖回调。

### 17.5 回调重复通知

重复回调命中已成功状态时，应直接返回第三方要求的成功响应，避免第三方继续重试。

### 17.6 回调签名校验

回调必须先验签，再进入幂等处理。验签失败不应创建幂等记录。

### 17.7 回调状态回退防护

业务状态机必须防止回调乱序导致状态回退。例如退款已成功后，不允许较早的退款处理中回调覆盖成功状态。

## 18. 安全与风控

### 18.1 Idempotency-Key 暴力提交

攻击者可能大量构造不同 Key 消耗 Redis 或数据库资源。必须配合限流、认证、长度限制和 TTL。

### 18.2 Key 长度限制

Key 长度应强制限制，避免超长 Key 造成索引膨胀或内存浪费。

### 18.3 用户维度限流

按用户 ID 限制单位时间内创建幂等记录的数量。

### 18.4 租户维度限流

SaaS 或开放平台场景应按租户、商户、应用维度限流。

### 18.5 敏感响应脱敏

幂等响应缓存中不得保存明文敏感数据。必要时只保存脱敏后的响应摘要。

### 18.6 幂等数据访问权限

幂等记录属于业务审计数据，后台查询和运维工具必须做权限控制。

### 18.7 日志中的敏感数据处理

日志中不得记录完整 Token、密码、身份证号、银行卡号、支付密钥和签名密钥。

## 19. 监控与告警

### 19.1 幂等命中率

监控重复请求命中比例。异常升高可能表示客户端重试过多、网络异常或接口超时。

### 19.2 Key 冲突次数

监控同 Key 不同请求体的冲突次数。异常升高可能表示客户端 Key 生成逻辑错误。

### 19.3 同 Key 不同请求体次数

该指标应作为安全和客户端质量监控重点。

### 19.4 PROCESSING 超时数量

长时间处理中的记录可能表示服务崩溃、第三方超时或补偿任务缺失。

### 19.5 UNKNOWN 状态数量

UNKNOWN 数量升高应触发告警，尤其是支付、退款、账务场景。

### 19.6 Redis 异常次数

监控 Redis 超时、连接失败、命令失败、锁获取异常。

### 19.7 数据库唯一索引冲突次数

唯一索引冲突过多可能表示幂等前置判断失效，也可能是客户端大量重试。

### 19.8 幂等记录保存失败次数

业务成功但幂等记录更新失败必须告警。

### 19.9 重复消息消费次数

监控消息重复投递和重复消费次数，用于评估 MQ 和消费者稳定性。

### 19.10 告警阈值建议

建议至少设置以下告警：

- `UNKNOWN` 状态数量超过阈值。
- `PROCESSING` 超过最大处理时长。
- 同 Key 不同请求体冲突突然升高。
- Redis 异常连续发生。
- 幂等记录保存失败。
- 支付、退款补偿任务积压。

## 20. 日志规范

### 20.1 必须记录的字段

应记录：

- Idempotency-Key。
- RequestHash。
- UserId 或 MerchantId。
- TenantId。
- ApiCode。
- BusinessId。
- IdempotencyStatus。
- TraceId。
- ErrorCode。

### 20.2 不应记录的字段

不应记录：

- 密码。
- Token。
- 银行卡号。
- 身份证号。
- 完整手机号。
- 支付密钥。
- 签名密钥。
- 完整敏感响应体。

### 20.3 重复请求日志

重复请求应记录命中状态、业务 ID 和返回策略，但不应打成错误日志。

### 20.4 冲突请求日志

同 Key 不同请求体应记录为警告日志，并包含作用域、接口、Key 和两个请求 Hash。

### 20.5 异常请求日志

系统异常和 UNKNOWN 状态应记录错误日志，并关联 TraceId、业务 ID 和补偿状态。

## 21. 过期与清理策略

### 21.1 幂等记录 TTL

TTL 必须按业务类型设置，不能所有接口统一使用很短时间。

### 21.2 不同业务的过期时间

| 业务      | 建议保留时间      |
| --------- | ----------------- |
| 普通提交  | 10 分钟到 24 小时 |
| 订单创建  | 24 小时到 7 天    |
| 支付/退款 | 7 天到 90 天      |
| 消息消费  | 7 天到 180 天     |
| 账务流水  | 长期或永久        |

### 21.3 过期后重复请求风险

幂等记录过期后，客户端重复请求可能再次执行。核心业务必须依赖业务唯一索引和状态机继续兜底。

### 21.4 历史数据归档

长期保留的记录应归档到历史表或冷存储，避免主表膨胀影响在线查询。

### 21.5 清理任务幂等

清理任务应支持重复执行。按主键范围或时间窗口分批清理，避免一次性大删除。

### 21.6 清理任务限速

清理任务应限制批次大小和执行频率，避免影响在线业务。

## 22. 风险清单

| 风险                       | 影响                                 | 建议方案                                      |
| -------------------------- | ------------------------------------ | --------------------------------------------- |
| Redis 故障                 | 无法判断短期幂等或获取锁。           | 核心业务 fail-close；依赖数据库唯一索引兜底。 |
| Redis 数据丢失             | 幂等缓存丢失，重复请求可能进入业务。 | 核心记录落库；Redis 仅做加速。                |
| 锁过期                     | 业务未完成时其他请求进入。           | 合理 TTL、必要时续期、数据库唯一索引兜底。    |
| 锁误释放                   | 释放其他实例锁。                     | 使用锁持有者标识校验。                        |
| 数据库唯一索引冲突         | 并发创建同一业务记录。               | 捕获冲突后查询已有业务结果。                  |
| 数据库主从延迟             | 读从库判断不存在导致重复执行。       | 幂等判断读主库或强一致读。                    |
| 业务成功但保存幂等响应失败 | 重复请求无法直接返回首次响应。       | 业务表可反查；保存业务 ID；告警补偿。         |
| 幂等记录过期清理           | 过期后重复请求可能再次执行。         | TTL 足够长；业务唯一索引兜底。                |
| 多实例部署                 | 本地锁失效。                         | 使用共享存储和分布式控制。                    |
| 第三方接口超时             | 不知道第三方是否成功。               | 进入 UNKNOWN；主动查询确认。                  |
| MQ 重复投递                | 重复消费造成重复副作用。             | 消费记录表 + 业务唯一约束。                   |
| 响应体过大                 | 存储成本高。                         | 缓存业务 ID 或响应摘要。                      |
| Key 被恶意刷爆             | Redis/DB 资源耗尽。                  | 限流、认证、TTL、长度限制。                   |
| 状态机回退                 | 旧请求覆盖新状态。                   | 状态流转约束和版本控制。                      |
| 补偿任务重复执行           | 重复调用外部或重复变更。             | 任务执行记录和业务状态判断。                  |

## 23. 测试清单

### 23.1 首次请求测试

验证首次请求能正常创建幂等记录，并完成业务处理。

### 23.2 重复成功请求测试

同 Key 同请求体重复请求，应返回首次成功响应。

### 23.3 同 Key 不同请求体测试

同 Key 不同请求体，应返回 409。

### 23.4 并发重复请求测试

多线程或多实例同时提交同一 Key，应只有一个请求执行业务逻辑。

### 23.5 正在处理状态测试

首个请求未完成时重复提交，应返回 409 或 202。

### 23.6 Redis 故障测试

模拟 Redis 不可用，验证核心接口是否按预期 fail-close 或使用数据库兜底。

### 23.7 数据库唯一索引冲突测试

模拟并发插入，验证冲突后能查询已有业务结果。

### 23.8 业务成功但响应保存失败测试

验证重复请求能通过业务表反查结果。

### 23.9 第三方超时测试

验证第三方超时时不会直接标记失败，而是进入 UNKNOWN 或处理中状态。

### 23.10 消息重复消费测试

同一消息重复投递，应只产生一次业务副作用。

### 23.11 幂等记录过期测试

验证记录过期后系统行为符合业务预期，核心业务仍有唯一索引兜底。

### 23.12 多实例并发测试

在多实例部署环境下验证幂等逻辑，不得依赖本地内存锁。

## 24. 接入规范

### 24.1 新接口是否需要幂等的判断标准

新接口评审时必须回答：

- 是否改变业务状态。
- 是否涉及资金、库存、权益、积分、优惠券。
- 是否可能被重试。
- 是否调用第三方。
- 是否存在重复提交风险。

只要任一答案为是，应评估接入幂等。

### 24.2 Controller / API 层接入方式

API 层适合处理：

- Header 校验。
- Key 格式校验。
- 请求体 Hash 计算。
- 通用状态码返回。

### 24.3 Application Service 层接入方式

应用服务层适合处理：

- 创建幂等记录。
- 判断已有状态。
- 调用业务服务。
- 保存业务结果或响应摘要。

### 24.4 Domain Service 层兜底方式

领域服务层应通过业务状态机保证重复执行不会造成错误状态流转。

### 24.5 Repository / 数据库唯一索引兜底

仓储和数据库层必须提供最终唯一性保障。关键业务不能只依赖上层判断。

### 24.6 中间件方案

中间件适合通用 HTTP 幂等，但对业务状态和事务边界感知较弱。核心业务仍需应用层和数据库兜底。

### 24.7 Filter / Attribute 方案

.NET 项目中可使用 Filter 或 Attribute 标记需要幂等的接口，统一做 Key 校验和请求 Hash 处理。

### 24.8 AOP 方案

对于 MediatR、Application Service 或命令处理器，可使用管道行为或 AOP 统一封装幂等逻辑。

```json
    "businessId": "123456"
  },
```


### 26.2 幂等记录表示例

```sql
CREATE TABLE idempotency_records (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NULL,
    user_id BIGINT NULL,
    merchant_id BIGINT NULL,
    api_code VARCHAR(128) NOT NULL,
    idempotency_key VARCHAR(128) NOT NULL,
    request_hash VARCHAR(128) NOT NULL,
    business_type VARCHAR(64) NULL,
    business_id VARCHAR(128) NULL,
    status VARCHAR(32) NOT NULL,
    response_code INT NULL,
    response_body TEXT NULL,
    error_code VARCHAR(128) NULL,
    error_message VARCHAR(1024) NULL,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NULL,
    expired_at DATETIME NOT NULL,
    UNIQUE (tenant_id, user_id, api_code, idempotency_key)
);
```

实际项目中应根据数据库类型、租户模型和用户模型调整索引。

### 26.3 Redis Key 命名示例


创建订单应同时使用：

- 优惠券核销幂等。
- 订单状态机。

### 26.7 支付提交示例流程

支付提交应同时使用：

- 支付流水号。
- 第三方幂等号。
- 支付单唯一索引。
- 支付状态机。
- 主动查询和回调确认。

### 26.8 退款申请示例流程

退款申请应同时使用：

- 退款流水号。
- 退款单唯一索引。
- 退款状态机。
- 渠道退款幂等号。
- 退款回调幂等。

### 26.9 消息消费示例流程

消息消费应同时使用：

- 消息业务 ID。
- 消费组。
- 消费记录表。
- 业务唯一索引。
- 消费状态机。

### 26.10 常见误区说明

常见误区：

- 只靠前端按钮禁用防重复提交。
- 只靠 Redis 锁，不做数据库唯一索引。
- 不校验请求体 Hash。
- 把 401、403、敏感数据、权限结果缓存为幂等响应。
- 第三方超时直接记为失败。
- MQ 消费只依赖 MessageId，不做业务唯一约束。
- 幂等记录过期时间过短。
- 多实例部署使用本地内存锁。
- 业务成功后幂等记录保存失败没有补偿。
