# 06-11 补偿任务实现

## 1. 目标

### 1.1 文档目的

定义 RabbitMQ 消费链路中补偿任务的生产实现方案，用于兜底消息重试和死信处理无法覆盖的业务最终一致性问题。

### 1.2 补偿任务解决的问题

补偿任务解决：

- 消息已经失败且进入人工处理池。
- 消费记录长时间 `Processing`。
- 订单已取消但库存未退回。
- 业务动作完成但消费记录未成功收尾。
- 死信消息无法直接重投。

### 1.3 与死信处理的区别

死信处理关注“这条消息为何失败以及如何处理”。补偿任务关注“业务最终结果是否正确”。

### 1.4 与 Retry 的区别

Retry 是消息消费管道中的自动重试。补偿任务是独立的业务修复流程。

## 3. 核心设计

### 3.1 为什么需要补偿任务

MQ 不能保证业务一定成功，只能保证消息尽量投递。最终业务一致性必须通过补偿任务兜底。

### 3.2 补偿任务类型

建议分为：

- Outbox 补偿监控。
- 消费记录补偿。
- 业务对账补偿。
- 死信处理补偿。
- 人工修复补偿。

### 3.3 Outbox 补偿

MassTransit EF Outbox 自带后台投递。项目需要补充监控：

```text
OutboxMessage 积压数量
最老未投递消息时间
RabbitMQ 连接异常
```

### 3.4 消费记录补偿

扫描：

```text
Processing 超时
Failed 且 RetryCount >= 5
Unknown
```

### 3.5 业务对账补偿

扫描：

```text
订单状态 = Cancel
且不存在库存退回流水
```

### 3.6 人工补偿

通过后台人工选择：

- 重投消息。
- 手动修复数据。
- 标记已处理。
- 创建补偿任务。

### 3.7 补偿任务幂等设计

补偿动作必须有业务唯一键，例如：

```text
SourceBusinessId = OrderId
SourceAction = ReturnStockForOrderCancel
```

## 4. 补偿任务分类

### 4.1 Outbox 投递补偿

依赖 MassTransit Outbox 投递服务。项目侧应做监控告警。

### 4.2 Processing 超时补偿

扫描：

```sql
SELECT *
FROM message_consume_records
WHERE status = 'Processing'
  AND processing_started_at < DATE_SUB(UTC_TIMESTAMP(), INTERVAL 5 MINUTE);
```

### 4.3 Failed 超限补偿

扫描：

```sql
SELECT *
FROM message_consume_records
WHERE status = 'Failed'
  AND retry_count >= 5;
```

### 4.4 订单取消未退库存补偿

扫描：

```sql
SELECT o.*
FROM app_orders o
LEFT JOIN stock_in_records s
  ON s.source_business_id = o.id
 AND s.source_action = 'ReturnStockForOrderCancel'
WHERE o.status = 'Cancel'
  AND s.id IS NULL;
```

### 4.5 死信消息补偿

由死信归集任务生成 `DeadLetterHandleRecord` 后，人工选择创建补偿任务。

### 4.6 人工修复补偿

人工修复必须写审计记录。

## 6. 订单取消退库存补偿流程

### 6.1 扫描已取消订单

查询 `AppOrderStatus.Cancel` 的订单。

### 6.2 判断库存流水是否存在

```sql
SELECT *
FROM stock_in_records
WHERE source_business_id = @OrderId
  AND source_action = 'ReturnStockForOrderCancel';
```

### 6.3 创建库存退回流水

如果不存在，创建 `StockInRecord`。

### 6.4 唯一索引冲突处理

如果插入时遇到重复键，视为其他实例已经补偿成功。

### 6.5 更新补偿记录

补偿成功后更新 `CompensationRecord` 为 `Success`。

### 6.6 告警或人工介入

补偿失败达到上限后通知运维。

## 11. 风险与未完成项

### 11.1 补偿重复执行风险

必须依赖业务唯一索引。

### 11.2 补偿误执行风险

执行补偿前必须判断订单当前状态。

历史数据、软删除、状态回退都可能影响判断。

多个补偿任务实例并发时必须用唯一索引或分布式锁兜底。
