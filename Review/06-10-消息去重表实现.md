## 3. 核心设计

### 3.1 为什么需要消息去重表

消费记录表用于记录每条消息对每个消费者的处理状态。即使 RabbitMQ 重复投递，也可以通过数据库记录判断是否需要再次处理。

### 3.2 MessageId + ConsumerName 唯一约束

推荐唯一键：

```text
MessageId + ConsumerName
```

原因：

```text
同一条消息可以被多个消费者分别消费。
每个消费者都应该独立记录自己的消费状态。
```

### 3.3 为什么不能只用 MessageId

如果只用 `MessageId` 唯一，则库存消费者消费后，优惠券消费者、通知消费者将无法写入自己的消费记录。

### 3.4 消费状态模型

```text
Unknown
Processing
Success
Failed
```

### 3.5 Processing 状态处理

规则：

```text
Processing 未超时：抛异常，让 MQ 稍后重试。
Processing 已超时：当前消费者接管处理。
```

### 3.6 Failed 状态处理

规则：

```text
Failed 且 RetryCount < 5：允许重试。
Failed 且 RetryCount >= 5：停止自动处理，进入人工补偿。
```

### 3.7 Success 状态处理

规则：

```text
Success：直接 return，MassTransit ACK。
```

### 3.8 Unknown 状态预留

当前代码遇到不支持状态会抛异常。后续可将 `Unknown` 纳入补偿任务。

## 5. 去重判断流程

### 5.1 首次消费

```text
查不到消费记录
 -> 插入 Processing
 -> 执行业务
 -> Success
```

### 5.2 重复成功消息

```text
查到 Success
 -> return
 -> ACK
```

### 5.3 Processing 未超时

```text
查到 Processing
 -> 未超过 5 分钟
 -> throw
 -> 稍后重试
```

### 5.4 Processing 已超时

```text
查到 Processing
 -> 超过 5 分钟
 -> 更新 ProcessingStartedAt
 -> 当前消费者接管
```

### 5.5 Failed 且 RetryCount 未达上限

```text
查到 Failed
 -> RetryCount < 5
 -> 改为 Processing
 -> 重新处理
```

### 5.6 Failed 且 RetryCount 达上限

```text
查到 Failed
 -> RetryCount >= 5
 -> 抛异常
 -> 进入 error queue 或人工补偿流程
```

### 5.7 并发插入唯一索引冲突

消费者捕获 `DbUpdateException` 并判断是否重复键。

当前实现：

```csharp
catch (DbUpdateException ex) when (IsDuplicateKeyException(ex))
```

后续建议进一步区分消费记录唯一键和业务唯一键。
