## 3. 核心设计

### 3.1 异常演练的目的

验证异常发生时系统是否能：

- 不重复执行业务。
- 不丢业务结果。
- 能进入重试或死信。
- 可通过补偿恢复。

### 3.2 可自动恢复异常

```text
短暂数据库异常
短暂网络异常
RabbitMQ 短暂不可用
Processing 未超时
唯一索引冲突可判定为幂等成功
```

### 3.3 需人工介入异常

```text
订单不存在
消息格式错误
RetryCount 达到上限
状态冲突
业务数据缺失
```

### 3.4 不可重投异常

```text
业务动作已经完成
订单状态已经不适合执行
消息内容错误且未修复
```

### 3.5 数据一致性验证标准

订单取消场景下应满足：

```text
订单状态 = Cancel
库存退回流水存在且只有一条
消费记录 = Success
```

## 4. 异常场景清单

### 4.1 RabbitMQ 不可用

预期：

```text
订单状态修改不受影响
OutboxMessage 保留待投递
RabbitMQ 恢复后继续发送
```

### 4.2 Outbox 写入成功但 RabbitMQ 暂不可用

预期同上。

### 4.3 Consumer 处理时数据库异常

预期：

```text
事务回滚
消费记录 Failed
消息重试
```

### 4.4 Consumer 处理成功但 ACK 前宕机

预期：

```text
RabbitMQ 重投
消费者命中 Success 或业务唯一索引
不重复退库存
```

### 4.5 消费记录 Processing 超时

预期：

```text
超过 5 分钟后新消费者接管
```

### 4.6 消费记录 Failed 达到上限

预期：

```text
停止自动业务处理
抛异常进入 error queue
等待人工补偿
```

### 4.7 库存流水唯一索引冲突

预期：

```text
视为幂等成功
消费记录 Success
```

### 4.8 订单不存在

预期：

```text
记录 Failed
视业务策略决定 ACK 或进入人工处理
```

当前代码会标记 Failed 并提交。

### 4.9 非 Cancel 状态消息

预期：

```text
标记 Success
说明当前消费者无需处理
```

### 4.10 重复消息投递

预期：

```text
同 MessageId 命中消费记录
同业务动作命中库存业务唯一键
```

### 4.11 消息进入 error queue

预期：

```text
消息保留在 error queue
运维后台或 Runbook 处理
```

### 4.12 手动重投死信消息

预期：

```text
处理前校验业务状态
避免无脑重投
```

### 7.3 Processing 超时 SQL

```sql
SELECT *
FROM message_consume_records
WHERE status = 'Processing'
  AND processing_started_at < DATE_SUB(UTC_TIMESTAMP(), INTERVAL 5 MINUTE);
```

FROM message_consume_records
WHERE status = 'Success';
