# 06-09 消费重试与死信队列

## 1. 目标

### 1.1 文档目的

验证当前 RabbitMQ 消费失败后的自动重试、错误队列以及死信处理规划是否符合生产环境要求。

### 1.2 验证范围

覆盖：

- MassTransit Retry 配置。
- `OrderStatusChangedConsumer` 异常抛出策略。
- `MessageConsumeRecord.RetryCount` 记录策略。
- error queue 处理规划。
- 死信归集与人工处置流程。

### 1.3 重试与死信的生产意义

重试用于恢复临时异常，死信用于承接自动恢复不了的问题。生产系统不能把死信当作失败终点，而应将其作为人工或半自动补偿入口。

## 3. 核心设计

### 3.1 自动重试设计

临时异常交给 MassTransit Retry：

- 数据库短暂不可用。
- 网络波动。
- 消费者处理中状态未超时。
- 并发冲突后需要稍后重试。

### 3.2 哪些异常允许重试

```text
数据库连接短暂失败
RabbitMQ 投递抖动
短时间锁冲突
Processing 未超时
下游服务短暂不可用
```

### 3.3 哪些异常应进入死信

```text
消息格式错误
订单不存在且确认不可恢复
RetryCount 达到上限
业务数据缺失
代码 Bug
字段长度或约束错误
状态机不允许流转且无法自动修复
```

### 3.4 MassTransit error queue 机制

消费者抛出异常后，MassTransit 根据 Retry 策略重试。重试仍失败，则消息进入 error queue。

### 3.5 RetryCount 与 MessageConsumeRecord 的关系

`RetryCount` 表示业务消费失败次数。消费者 catch 普通异常时增加：

```csharp
record.RetryCount++;
```

MassTransit 的 Retry 次数和业务表中的 `RetryCount` 是两个层面：

```text
MassTransit Retry：消息管道重试。
MessageConsumeRecord.RetryCount：业务失败追踪。
```

### 3.6 死信处理职责边界

死信处理不应直接无脑重投，应先检查：

- 消费记录是否已经 `Success`。
- 库存流水是否已经存在。
- 订单当前状态是否仍需要处理。
- 错误原因是否已经修复。

### 3.7 死信不是最终失败，而是人工处理入口

死信处理目标不是让消息机械消费成功，而是让消息对应的业务结果最终正确。

## 4. 重试流程

### 4.1 Consumer 处理失败

消费者抛出异常：

```csharp
throw;
```

### 4.2 MassTransit 自动重试

按照：

```text
6 次，每次间隔 10 秒
```

进行重试。

### 4.3 重试成功

消费者正常返回，MassTransit ACK。

### 4.4 重试失败

重试超过上限后，消息进入 error queue。

### 4.5 进入 error queue

预期队列：

```text
order-status-changed-queue_error
```

## 5. 死信处理流程

### 5.1 死信消息来源

- RabbitMQ error queue。
- `message_consume_records` 中 `Failed` 且 `RetryCount >= 5`。
- `Processing` 超时记录。
- 后续规划中的 `Unknown` 记录。

### 5.2 死信消息字段

建议归集字段：

```text
MessageId
ConsumerName
QueueName
BusinessType
BusinessId
Payload
Headers
ErrorMessage
RetryCount
TraceId
```

### 5.3 死信处理前置检查

```sql
SELECT *
FROM message_consume_records
WHERE message_id = @MessageId
  AND consumer_name = 'OrderStatusChangedConsumer';
```

```sql
SELECT *
FROM stock_in_records
WHERE source_business_id = @OrderId
  AND source_action = 'ReturnStockForOrderCancel';
```

### 5.4 可重投场景

- 错误原因已经修复。
- 消费记录不是 `Success`。
- 业务动作尚未完成。
- 订单状态仍然需要处理。

### 5.5 不可重投场景

- 消费记录已经 `Success`。
- 库存流水已经存在。
- 订单状态已经不适合执行该动作。
- 消息格式错误且未修复。

### 5.6 人工修复场景

- 数据缺失。
- 状态冲突。
- 历史错误数据。
- 无法通过重投恢复。

### 5.7 标记已处理场景

业务动作已完成，但死信仍存在时，应标记死信处理记录为已处理，不重投。

## 10. 风险与未完成项

### 10.1 无脑重投风险

重投前必须查询业务状态，避免重复退库存。

### 10.2 error queue 积压风险

缺少 error queue 积压告警。

### 10.3 Retry 风暴风险

大量消息同时失败会造成重复重试，需要配合限流和告警。
