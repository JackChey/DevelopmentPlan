## 2. 背景

```sql
SELECT
    a.Id,
```

## 6. 执行计划分析

### 6.1 优化前

- `type = ALL`
- `possible_keys = null`
- `key = null`
- `rows = 96470`
- `Extra = Using where`

结论：
数据库未命中可用索引，查询退化为全表扫描。

### 6.2 优化后

- `type = ref`
- `possible_keys = IX_app_orders_UserId, IX_app_orders_UserId_OccurredTime`
- `key = IX_app_orders_UserId`
- `rows = 360`
- `Extra = null`

结论：
数据库已命中 `UserId` 索引，扫描行数显著下降。

## 7. 根因分析

本次慢 SQL 的根因是：

`app_orders.UserId` 条件列缺少有效索引，导致按 `UserId` 过滤时执行计划退化为全表扫描。`

证据链如下：

1. 查询语句核心条件为 `WHERE a.UserId = @_query_Id_0`
2. 无索引时 `EXPLAIN.type = ALL`
3. 无索引时 `key = null`
4. 无索引时扫描行数达到 `96470`
5. 有索引时 `EXPLAIN.type = ref`
6. 有索引时命中 `IX_app_orders_UserId`
7. 有索引时扫描行数下降到 `360`

因此可以确认：
本次性能问题的主要根因是 `UserId` 条件列缺索引，而不是 N+1、多 SQL、排序失效或响应结构异常。

## 8. 优化动作

本次优化动作如下：

1. 为 `app_orders.UserId` 增加普通索引 `IX_app_orders_UserId`
2. 增加组合索引 `IX_app_orders_UserId_OccurredTime`
3. 保持查询语义不变，仅优化过滤列命中索引能力

优化目标：
降低按 `UserId` 条件查询时的扫描行数，使执行计划从全表扫描切换为索引命中。

## 10. 风险与限制

1. 本次属于本地演练，不等同真实线上慢查询事故
2. 诊断接口仅用于演练，不对外暴露
3. 单次接口耗时波动较大，不能仅凭一次 `DurationMs` 作为唯一结论
4. 新增索引会增加写入维护成本，但对当前按 `UserId` 查询订单场景是合理代价
